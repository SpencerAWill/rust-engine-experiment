# Changelog

All notable changes are recorded here, in the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) style. The crates are `0.x` and `publish = false`, so any release may break compatibility; breaking changes are marked **breaking**. The PRNG output streams and `UntypedGenId::to_bits` (which `GenId::to_bits` forwards to) are frozen for all of `0.x` and will not change.

## [Unreleased]

### Changed

- **Spike workloads whose state keeps changing (M3.26):** `frag_iter`'s step now adds 0.618034 and wraps into `0.0..1.0`, and `heavy_compute`'s step moves the matrix's translation by `velocity * dt` after its 100 inversions, so every entity's state changes every tick and conformance can see a skipped or repeated step. Before, every `frag_iter` value settled on one number by tick 26, and by about tick 20 the even inversion count returned 963 of 1,000 `heavy_compute` matrices bit for bit each step. `heavy_compute::update` takes `&Velocity`, and `sparse_set_grouped`'s `heavy_compute` group is `(Matrix, Position, Rotation, Velocity)`. Every ECS `add_remove` backend gains a test that its insert pass reaches every entity on every step. Spike rows for `frag_iter` and `heavy_compute` from earlier runs measured the old rules, so they do not compare with later runs ([spec](docs/chunks/m3.26-workload-checks-that-fail/spec.md)).
- **Pause after the plan (#135, #137):** the chunk loop now waits three times: stage 3 stops after the plan commit with a one-line reminder to run `/rename <id> spec and plan`, `/clear` and `/chunk resume`, which continues at stage 4 from disk, so the work and review stages do not carry the brainstorm and grill conversation ([docs/workflow.md](docs/workflow.md#the-loop)). Saying "continue" goes on in the same session. A chunk no longer has to run in one session.
- **Planning state on GitHub (M3.20):** what is scheduled, its order, its milestone and its status moved from `docs/roadmap.md` to GitHub ([docs/workflow.md](docs/workflow.md#from-issue-to-chunk)). Every chunk is one issue titled `M<N>.<n>: <title>` and authored by the maintainer's account; scheduled work is ordered by a numeric `Order` field in the "Engine backlog" Project and "blocked by" links; `/chunk next` reads them and skips chunks in flight (their branch is pushed in stage 1). Small scheduled work without a chunk ID is a chore, run by `/chunk chore #N` as one pull request, its commits ending ` (#N)`. Milestones M3 to M9 are GitHub milestones declared in `infra/github/index.ts` (`retainOnDelete`); the per-milestone tracking issues #66 and #67 close. `docs/roadmap.md` keeps the milestone goals and exit criteria, the later milestones' rough lists and the chunk tables up to M3.20 as history. `/triage` checks the `Order` field and never schedules.
- **Issue tracking (M3.18):** one documented path from an idea to a merged chunk ([docs/workflow.md](docs/workflow.md#from-issue-to-chunk)): issues are triaged in a GitHub Project (Status, Priority, Size) and, once scheduled, owned by the roadmap; an issue is Ready when it meets a Definition of Ready; larger work is a tracking issue with one sub-issue per chunk. The bug, feature and infrastructure templates are now issue forms that ask for the outcome and its verification, `area:*`, `needs-measurement` and `ai-assisted` labels are declared in Pulumi, and `/triage` (`.claude/skills/triage/`) defines and orders issues using only `gh` and file reads, so it can run while a long test or benchmark occupies the machine. Chunk stage 1 reads the linked issue and marks it Scheduled.
- **Documentation layout (M3.16):** each directory that matters has a README in one shape (status, "When this applies", "Contents"), and the tool manuals moved out of `CONTRIBUTING.md` next to their tools: benchmarks and the instruction-count gate to `bench/README.md`, fuzzing to `fuzz/README.md`, the command reference, coverage and mutation testing to `xtask/README.md`, spike crates to `spikes/README.md`. The rules in those manuals that bind library code (inline test modules, no coverage or mutants attributes, a fuzz crash becomes a failing test first) are now in `CONTRIBUTING.md` "Tests". New `cargo xtask check-docs`, a required check (job `check-docs`): required READMEs and their Contents, relative links and heading anchors in every Markdown file, lesson and `.claude/rules/` frontmatter, and `AGENTS.md` under 80 lines; it uses `pulldown-cmark`. `.claude/rules/` points Claude Code at the README of the path it touches. `bench-regress` no longer treats Markdown files as able to change an instruction count. The broken links of #58 are fixed.
- **Agent workflow (M3.15):** work runs as one loop per chunk (brainstorm, grill, plan, work, review, compound, close out) that waits for the maintainer only at spec approval and the merge go-ahead ([docs/workflow.md](docs/workflow.md)). `.claude/` now holds agent roles with pinned models (Sonnet builders; independent reviewers on Opus or Sonnet), the `/chunk`, `/grill`, `/lessons-refresh`, `/bench-run` and `/mutants-run` skills, a read-only command allowlist, and a hook that blocks agent pushes to `main` and force pushes (`cargo xtask guard-push`). Each chunk keeps an append-only `log.md`; lessons live in `docs/lessons/` and are read by path when planning. Chunk folders moved from `docs/design/m<N>-<topic>/` to a flat `docs/chunks/`; `AGENTS.md` is shorter, and `CLAUDE.md` imports it.
- **One library crate (M3.13), breaking:** the library is one crate, `engine`, and every item is reached through its modules (`engine::genid`, `engine::collections`, `engine::random`, `engine::time`, `engine::math`) as before. `math` builds without `std`: without it, `math::scalar` and glam use `libm`, so `cargo xtask no-std` builds all of `engine`. [ADR 0004](docs/adr/0004-crate-splitting-rule.md) now gives the rule for when a separate crate is made, and [ADR 0003](docs/adr/0003-same-build-determinism.md) states the transcendental backends. `cargo xtask mutants` selects modules with `--module` (it replaces `-p`), and its summary and the coverage summary have one row per module. The Criterion subjects are named after the types they measure (`engine::GenIdMap`, `engine::GenIdAllocator`, `engine::Prng`, `engine::IndexMap`), so saved baselines from before this change no longer compare; `docs/benchmarks.md` is re-recorded.
- **Generational IDs (M3.11), breaking:** `engine::handle` is now `engine::genid`. `Handle<T>` is `GenId<T>`, `HandlePool<T>` is `GenIdMap<T>`, `HandleAllocator<T>` is `GenIdAllocator<T>` and `InvalidHandleBits` is `InvalidGenIdBits`; the old names are gone, with no aliases. `DenseHandleAllocator` and its iterator are removed: use a `GenIdMap<()>` to iterate live IDs. New: `UntypedGenId`, the ID without its type, with `GenId::untyped` and `GenId::from_untyped`; the bit encoding is unchanged and now documented on `UntypedGenId::to_bits`. The renamed fuzz targets (`genid_from_bits`, `genid_map_ops`, `genid_allocator_ops`) start with an empty corpus. [ADR 0012](docs/adr/0012-generational-ids.md) supersedes ADR 0010. `GenIdMap::capacity` now returns the smaller of the ID and value capacities; for a zero-sized `T` such as `()` it used to return `usize::MAX`. Entries below that name the old types are history.
- **Repository settings (M3.9):** pull requests are squash-merged with the pull request title as the commit subject, and `main` requires linear history. Private vulnerability reporting (through a Pulumi dynamic resource, since the provider has no resource for it), Dependabot security updates and repository topics are declared in `infra/github`, and the unused wiki and Projects are turned off. New CodeQL (`actions` and `rust`) and weekly OpenSSF Scorecard workflows report to the Security tab without blocking merges. `check-workflows` gains rule 5: a `write` token scope is allowed only for a job in `WRITE_ALLOWLIST` (the two scanning jobs). Dependabot version updates wait 7 days after a release.
- **Repository layout:** the bench packages live under `bench/`: `benches/` is now `bench/compare/` and `bench-regress/` is `bench/regress/`. The package names (`engine_benches`, `engine_bench_regress`) and every command are unchanged. `cargo xtask bench-regress` still compares with a base commit from before the move, by finding the package at its earlier location.
- **Issue templates:** new templates for a determinism bug and a performance report (issue forms whose required fields ask for what [ADR 0003](docs/adr/0003-same-build-determinism.md) and the benchmark rules need) and for infrastructure or chore work. The bug report sends determinism bugs to the new form, and the feature request is narrowed to engine features and design changes. New labels `infrastructure`, `performance` and `determinism`; Discussions are enabled for questions and linked from the issue chooser. `CONTRIBUTING.md` lists which template to use for what.
- **Roadmap (M3.0):** M3 is current and broken into chunks M3.0 to M3.8, the storage prototypes are kept under `spikes/` after the decision, M4 is next, and M7 gains the open question of how systems send events to each other.
- **Devcontainer:** the image is now Debian trixie (Valgrind 3.24, which the instruction-count gate needs), the Node feature was added (trixie's `nodejs` has no `npm`, which the Claude Code feature requires), and `install-tools.sh` installs Valgrind and `gungraun-runner`.
- **Dependencies:** updated `glam` to 0.34 (from 0.30) and `xtask`'s `syn` to 3. glam 0.33 made every non-`f32` type an opt-in feature, so `engine::math` now enables `f64`, `i32` and `u32` to keep exactly the same public types. The layout assertions, goldens and the `fixed_step_sim` checksum are unchanged.
- **Toolchain:** pinned Rust is now 1.100.0 (from 1.97.0), and `rust-version` (the MSRV) is 1.100. `Prng::fill_bytes` uses `as_chunks_mut` (a new clippy lint); its output is unchanged and covered by the golden tests.
- **CI:** `ci.yml` runs on pushes to `main` and on pull requests, no longer on every push, so a branch with an open pull request does not run every job twice. `actions/checkout` 7.0.1 and `actions/upload-artifact` 7.0.2 (still pinned to commit hashes), and the devcontainer `rust` feature 1.6.1.
- **Process:** work is now planned in `docs/roadmap.md` as small chunks, each with a spec and plan from `docs/chunks/_template/`. Milestones after M0+M1 are renumbered (the roadmap maps old to new numbers); plans are kept as historical records, and the M0+M1 plan is restored.

### Added

- **many_queries workload (M3.22):** a ninth ECS storage spike workload, in which each step runs 56 two-component queries over eight archetypes of four types, so the fixed cost of starting a query is a large share of the step, for the M3 storage decision ([spec](docs/chunks/m3.22-many-queries/spec.md)). The harness's `for_each_query!` macro lists the queries once, and every ECS backend runs its step through it. It runs on `vec_aos`, `archetype`, `sparse_set`, `dense`, `hybrid`, `bevy_ecs` and `hecs`, at 100 to 10,000 entities in both spike benches.
- **random_access workload (M3.21):** an eighth ECS storage spike workload, in which every entity reads its target's position by handle each step and stale handles are retargeted, for the M3 storage decision ([spec](docs/chunks/m3.21-random-access/spec.md)). It runs on `vec_aos`, `archetype`, `sparse_set`, `dense`, `hybrid`, `bevy_ecs` and `hecs`, at 10,000 to 1,000,000 entities in both spike benches. The four prototypes gain `World::lookup::<T>()`, a read-only `Lookup` that reads one component type by handle with the type resolved once.
- **bevy_ecs and hecs baselines (M3.10):** `spikes/ecs_storage/bevy/` (`spike_ecs_bevy`) and `spikes/ecs_storage/hecs/` (`spike_ecs_hecs`) run the seven spike workloads on `bevy_ecs` 0.20 and `hecs` 0.11, as measurement baselines for the M3 storage decision (no code taken from either). Three backends pass conformance against `vec_aos`: `bevy_ecs` (table storage) and `hecs` for every workload, and `bevy_ecs_sparse` (`B` and `Seeker` in bevy's `SparseSet` storage) for `add_remove` and `agents`. They are registered in both spike benchmarks. Each drives its `World` directly on one thread, with no schedule or batch API, so the rows measure storage as the prototypes' do. `deny.toml` bans both libraries except through these crates, and these crates except through the spike benches. Expected, unmeasured: `bevy_ecs` and `hecs` within a small factor of `archetype` on iteration; `bevy_ecs_sparse` near `hybrid` on `add_remove`, although bevy still moves the entity to another archetype, which `hybrid` does not; `hecs` pays a lock, a type lookup, a downcast and an `Arc` clone per query run for its query cache. `hecs` turns on `hashbrown` 0.17.1's `inline-more` and `default-hasher`, and `bevy_ecs` turns on `indexmap`'s and `foldhash`'s `std` (the changed features of crates the spike code calls), for every backend the spike benches build, a build change whose effect is unmeasured (no spike source uses `IndexMap` or `IndexSet`, so it is expected to be small), so spike rows are compared within one run, not with runs from before M3.10. `cargo xtask bench` now excludes every spike package, so `engine` and its normal dependencies build with the same features as before. No change to `libs/`.
- **Runtime-registered components (M3.6):** the archetype prototype (`spike_ecs_archetype`) stores components that have no Rust type, for the M3 decision on component identity and on foreign and mod-defined component storage: `World::register_raw` gives an id to a component known only by its `RawLayout` (size, and alignment up to 16; plain data), byte columns hold its values beside the typed columns in the same tables and move through the same cached edges, and `spawn_raw`, `insert_raw`, `remove_raw` and `get_raw` validate every input (`RawError`). `RawQuery` runs by id and hands out one table's columns at a time, as byte rows or, through `bytemuck`, as slices of a `Pod` type. Two harness backends, `archetype_bytes_copy` (values copied through a codec) and `archetype_bytes_cast` (columns cast to `Pod` slices), pass conformance against `vec_aos` for `simple_iter`, `add_remove` and `frag_iter` and are registered in both spike benchmarks. New dependency `bytemuck` 1.25.2, for this spike crate only. No change to `libs/`.
- **Per-component hybrid prototype (M3.5):** `spikes/ecs_storage/hybrid/` (`spike_ecs_hybrid`), a minimal safe ECS for the M3 storage comparison in which each component type chooses its storage through its `Component` impl (`type Storage = TableStorage` or `SparseStorage`): archetype tables with cached transition edges and bundle spawn by default, or a sparse set of its own, so inserting or removing a sparse type moves no row and changes no archetype. One query layer over both picks each fetch at compile time, reads table columns as slices and probes a sparse set per row only for the sparse types a query names; `Commands` and `check_invariants` cover both kinds. One harness backend, `hybrid` (`B` and `Seeker` sparse, every other type a table type), passes conformance against `vec_aos` for all seven workloads and is registered in both spike benchmarks. Expected, unmeasured: `add_remove` near `sparse_set`, and the five workloads that name no sparse type within noise of `archetype`; the informal run in PR #89 instead put `agents` above `archetype`, which M3.8 measures. No change to `libs/`.
- **Dense-array prototype (M3.19):** `spikes/ecs_storage/dense/` (`spike_ecs_dense`), a minimal safe ECS on dense per-entity arrays for the M3 storage comparison: a `World` with one column per component type, a `Vec<Option<T>>` indexed by entity index beside a presence `HierarchicalBitSet` (kept in step by one private type), inserts and removals that write one slot and one bit and move nothing, the same typed tuple queries and `Commands` as the other prototypes driven by `engine::collections::Join` over the required and excluded presence sets, and `check_invariants`. One harness backend, `dense`, passes conformance against `vec_aos` for all seven workloads and is registered in both spike benchmarks. Expected, unmeasured: its best case is `add_remove` and respawning, its iteration is slower than archetype tables (one index at a time, an `Option` check per fetch), and its memory cost of a slot per entity per type shows only in space numbers (#41). No change to `libs/`.
- **Archetype prototype (M3.4):** `spikes/ecs_storage/archetype/` (`spike_ecs_archetype`), a minimal safe ECS on archetype storage for the M3 storage comparison: a `World` with one table per distinct set of component types (an entity list and one column per type, kept the same length by one private type), inserts and removals that move an entity's row between tables through cached add and remove edges, `spawn_with` for flat bundles of 1 to 8 components placed straight into their table, the same typed tuple queries (`query`, `query_mut`, `Option`, `Entity`, nested tuples, chained `.with::<T>()` and `.without::<T>()`) and `Commands` as the sparse-set prototype, and `check_invariants`. Unlike the sparse-set prototype, a query with no required type visits every live entity. One harness backend, `archetype`, passes conformance against `vec_aos` for all seven workloads and is registered in both spike benchmarks. No change to `libs/`.
- **Sparse-set prototype (M3.3):** `spikes/ecs_storage/sparse_set/` (`spike_ecs_sparse_set`), a minimal safe ECS on sparse-set storage for the M3 storage comparison: a `World` with one sparse set per component type and a live count, owning groups declared on a `WorldBuilder` (kept as aligned prefixes on every insert, remove and despawn), typed tuple queries (`query` for reads, `query_mut` for writes) over `&T`, `&mut T`, `Option`, `Entity` and nested tuples with chained `.with::<T>()` and `.without::<T>()` filters, a `Commands` buffer applied after a query, and `check_invariants`. Two harness backends, `sparse_set` for all seven workloads and `sparse_set_grouped` for six, pass conformance against `vec_aos` and are registered in both spike benchmarks. No change to `libs/`; a query with no required type panics in this prototype (M4 will match every live entity).
- **`engine::collections::HierarchicalBitSet` and `Join` (M3.17):** a set of indices in six fixed layers of `u64` words, where each upper bit records whether a word below is non-zero, so iteration skips empty ranges; `MAX_BITS` is `u32::MAX` on every target, as for `BitSet`. `Join` iterates the indices in every one of a run-time list of required sets and in none of a list of excluded sets, without allocating. In-place union, intersection and difference, subset and disjointness tests, conversions to and from `BitSet`, and a public `check_invariants`. Dense only: memory follows the highest index (about `index / 8` bytes). Our own code, with no new dependency (`hibitset` and `hi_sparse_bitset` are benchmark baselines only). New `EmptyJoinError` and `BitSetInvariantError`, a `hierarchical_bit_set_ops` fuzz target in the nightly job, instruction-count and wall-clock benchmarks, a `dhat` space report (`bench/compare/examples/space_report.rs`), and a mutation triage.
- **`engine::collections::BitSet` and `BitArray` (M3.14):** sets of small indices stored one bit per index in `u64` words. `BitSet` grows on insert and has a fixed `MAX_BITS` (`u32::MAX`) so behaviour does not depend on pointer width; `BitArray<WORDS>` is inline and never allocates. Both have set algebra in place, subset and disjointness tests, ascending double-ended iteration, read access to the words in a documented layout, and equality and `Hash` that ignore capacity. Our own code, with no new dependency (`fixedbitset` is a benchmark baseline only). New `BitIndexError`, and a `bit_set_ops` fuzz target in the nightly job. Instruction-count and wall-clock benchmarks and a mutation triage are included.
- **Research catalog:** `docs/research/data-structures.md` lists 243 data structures used in game engines, in 29 sections. Each entry gives uses, notes, variants, fit with the repo's rules, what a spec must define to stay deterministic, the entries it builds on, and sources; 61 entries are marked as having no source checked yet. It is external research, not a decision; the tracking issue (#38) holds one checkbox per entry. New label `research` for that issue and its sub-issues.
- **Spike harness (M3.2):** `spikes/`, a home for measured experiments with one directory per topic, and its first spike, `spikes/ecs_storage/`. `spike_ecs_harness` defines seven storage workloads (simple and fragmented iteration, heavy compute, add/remove, entity churn, 100k 2D sprites, the M3.0 agent workload) precisely enough for any backend to reproduce them, with a `Workload` trait, the `Fnv1a` hash builder and `check_conformance`, which names the first tick at which a backend's checksum differs from the reference's. `spike_ecs_vec` holds the plain-`Vec` reference backends (array-of-structs for every workload, struct-of-arrays for agents). `cargo xtask spike-bench ecs [--save NAME]` runs the Criterion bench (`spike_ecs_bench_compare`), and `cargo bench -p spike_ecs_bench_cache` runs the Gungraun bench with Callgrind's cache simulation. `bench` and `bench-doc` leave the spike benchmarks out, `bench-smoke` runs them once, and `coverage` and `check-statics` know the spike packages. `CONTRIBUTING.md` gains the rules for spike crates (no doctests or `try_` twins, outside coverage and mutation testing, conformance before numbers). No change to `libs/`; bevy_ecs and hecs baselines move to the new chunk M3.10.
- **`engine::collections` (M3.1):** `IndexMap<K, V>` and `IndexSet<T>`, `no_std` hash collections whose iteration order is insertion order, so it is a pure function of the operations applied and never depends on hashing, platform or crate versions. Removal is `swap_remove` or `shift_remove` (no bare `remove`), equality and `Hash` respect order, and `sort_keys`/`sort` give a canonical order. Backed by `indexmap` and `foldhash` (fixed seed, not part of the contract). Re-exported as `engine::collections` (not in the prelude). `clippy.toml` now also bans `indexmap`'s and `foldhash`'s randomly seeded types and constructors. Instruction-count and wall-clock benchmarks, and a mutation triage, are included.
- **`agents_2d` example (M3.0):** `examples/agents_2d`, 10,000 2D agents that wander, bounce, gain and lose a seeker part, and respawn, in a `winit` and `softbuffer` window (`cargo run -p agents_2d --release`, or `-- --headless` for a printed summary). The rules are written down in the M3.0 spec, and `Sim::checksum` is a wrapping sum of per-agent hashes that does not depend on storage order, so the M3 storage prototypes can be checked against it. `winit` 0.30 and `softbuffer` 0.4 are dependencies of this example only (not of any package under `libs/`); `winit` is built without its `wayland-csd-adwaita` feature, whose font crates fail `cargo deny`.
- **Instruction-count gate (M2.4):** `cargo xtask bench-regress [--base REV] [--report-only]` counts CPU instructions under Valgrind through Gungraun for 16 benchmarks of `engine::handle` and `engine::random` (new package `engine_bench_regress` in `bench-regress/`), at a base commit and at the working tree, and fails when any count rose by more than 5%. A required `bench-regress` workflow runs it on pull requests against the current tip of `main`; the `perf-regression-accepted` label makes a regression report-only. Also `cargo xtask gungraun-version`, and `bench-smoke` now runs the Gungraun benchmarks in test mode (it needs `gungraun-runner`).
- **Mutation testing (M2.3):** `cargo xtask mutants [--module NAME]... [-j N] [--list] [--in-diff FILE]` runs `cargo-mutants` (pinned at 27.1.0) on `engine::handle` and `engine::random` with shared settings in `.cargo/mutants.toml`, checks the exclusion list, and prints a per-module table; a weekly, report-only `mutants` workflow (every mutant on a schedule, only the mutants in changed code on pull requests that touch the triaged modules or the tooling); and the first triage, recorded in `docs/mutation-triage.md`.
- **Coverage (M2.2):** `cargo xtask coverage [--open]` measures line and function coverage of the library and example sources through `cargo-llvm-cov` (a per-crate table that leaves out `#[cfg(test)]` items, plus HTML and lcov reports), and a report-only `coverage` job in CI writes the table to the job summary and uploads the reports. No threshold. The `ci` description now says it runs every check CI gates on; report-only jobs run outside it.
- **Fuzzing (M2.1):** four `cargo-fuzz` targets for `engine::handle` (operation sequences for `HandlePool`, `HandleAllocator` and `DenseHandleAllocator` against reference models with `check_invariants` and drop accounting, plus `Handle::from_bits`), `cargo xtask fuzz`, `fuzz-build` and `fuzz-toolchain`, a pinned nightly, a PR-time `fuzz-build` job, and a nightly `fuzz` job with a cached corpus.
- **Workspace and policy (M0):** pinned toolchain, lint policy, determinism bans in `clippy.toml`, `cargo-deny`, dual MIT/Apache licensing, ADRs 0001-0011, and `cargo xtask` (fmt, clippy, test, doc, deny, no-std, wasm, check-unsafe, check-statics, check-workflows, bench, bench-smoke, bench-report, prng-stats, ci). GitHub Actions are pinned to commit hashes and use a read-only token.
- **`engine::handle`:** typed generational `Handle<T>`; dense `HandlePool<T>` with 8-byte slots; the lean `HandleAllocator<T>` and the iterable `DenseHandleAllocator<T>`; `reserve`/`try_reserve`, `with_fixed_capacity`, `insert_with`, `allocate_many`; `From`/`TryFrom<u64>` for `Handle`.
- **`engine::random`:** `Prng` (xoshiro256++ seeded by SplitMix64) with normative sampling algorithms and frozen output streams.
- **`engine::time`:** `Tick`, `Timestamp`, `TimeSource`, `ManualClock`, `SystemClock`, `FixedTimestep`.
- **`engine::math`:** glam re-exports, a transcendental funnel (`scalar`), `Transform`, large-world `WorldTransform`, 2D variants, coordinate conversion (`ENGINE`, `GLTF`, `UNITY` presets).
- **`engine`:** facade crate and prelude. **`examples/fixed_step_sim`:** a deterministic headless simulation with a golden checksum that is identical on aarch64 and x86_64.
- Comparison benchmarks against `slotmap`, `thunderdome`, `rand`, `rand_xoshiro` and `fastrand`, and `cargo xtask bench-report` for HTML reports of saved results.

### Fixed

- **`check-unsafe`** checks every workspace member, read from `cargo metadata`, instead of a hard-coded list that left out `bench-regress` (`engine_bench_regress`), and it now works when started from a subdirectory (it used to find no crates there and pass). That crate already forbade `unsafe`, so nothing else changed.
