# M2.2 plan: Coverage

- **Status:** Historical: executed in PR #16 (2026-11-12); the spec and the code are authoritative
- **Spec:** [spec.md](spec.md). This plan argues from the spec; read both.

## 1. Approach

Six commits on branch `m2.2-coverage` (the spec commit is already on it). The summary code comes first, as pure functions with unit tests, because it carries the chunk's only non-trivial logic (the `#[cfg(test)]` filter and the lcov parser) and needs no tool to test. The command that runs `cargo-llvm-cov` and feeds the summary comes next, then the workflow and devcontainer, then the docs, then the closing record once CI has run.

Choices the spec leaves to implementation:

- **Probe before code (no commit).** Install `cargo-llvm-cov` and `llvm-tools-preview` locally and run the spec's commands by hand once, from the repository root, to confirm what the spec took from documentation: that `cargo llvm-cov nextest --no-report` followed by `cargo llvm-cov report --html --output-dir target/llvm-cov` writes `target/llvm-cov/html/index.html`; the exact `FN` form LLVM writes in lcov (`FN:<line>,<name>` or `FN:<line>,<end>,<name>`); whether names are mangled or demangled (demangled names can contain commas); and that `SF` paths are absolute and resolved. Write the findings into §4 Deviations if any contradicts the spec, and stop to ask if one changes a requirement. Keep one real `lcov.info` excerpt in mind for the fixtures, but write the fixtures by hand (they are a few lines each).
- **Module layout.** `xtask/src/coverage.rs` holds the command; `xtask/src/coverage/summary.rs` holds the lcov parser, the test-item finder and the renderer (the spec's §4.1 allows the split, and the summary alone will be about 250 lines with tests). `coverage.rs` declares `mod summary;`.
- **Opening the report.** `--open` re-runs the HTML report command with `--open` added (`cargo llvm-cov report --html --open --output-dir target/llvm-cov ...`), so `xtask` needs no platform opener of its own.
- **Reading files.** The summary takes a `read_source: impl Fn(&Path) -> Result<String, String>` instead of touching the disk, so its tests feed sources from a `BTreeMap`. Only `coverage()` passes `std::fs::read_to_string`.

**Global constraints**

- Every commit passes `cargo xtask ci --quick`; the commits that touch a workflow also pass `cargo xtask check-workflows`.
- Commit messages are conventional, end with ` (M2.2)`, and end with the attribution lines the session requires. Stage by explicit path.
- No new dependency in `xtask/Cargo.toml` (`syn`, `proc-macro2` with `span-locations`, and `serde_json` are already there; the summary does not need `serde_json`).
- No change under `libs/`, `examples/`, `infra/` or to `rust-toolchain.toml` (R12, R13).
- Stop and ask the maintainer before the first push of the branch (Step 4 needs CI to run the job) and before opening the pull request.

**Review focus** (failure modes the spec implies that no requirement's test pins on its own; each has a test in the step that owns the code)

1. **Demangled function names with commas** (`<Foo<A, B> as Bar>::baz`) split into the wrong fields. The `FN` and `FNDA` parsers take the numeric fields from the left and treat the rest of the record as the name. Test in Step 2: `fn_record_name_may_contain_commas`.
2. **Both `FN` forms.** LLVM versions differ on whether `FN` carries an end line. The parser accepts `FN:<line>,<name>` and `FN:<line>,<end>,<name>` (the second field is an end line exactly when it parses as a number, which a Rust symbol never does). Test in Step 2: `fn_record_accepts_an_optional_end_line`.
3. **A root that does not match LLVM's paths** (symlinked checkout, a trailing separator) makes every file an "outside the patterns" error, or, with the regex, excludes everything. The root is canonicalized once in `coverage()`; the summary errors on zero counted files. Tests in Step 2 (`no_counted_file_is_an_error`) and Step 3 (`ignore_regex_escapes_and_anchors_the_root`), plus the local run from a path reached through a symlink in Step 3's verification.
4. **Test items that `syn` sees differently from the compiler**: an attribute written as `#[cfg(test)]` on a `use` line, on a `const`, or on a nested `mod` inside a non-test `mod`. The finder visits every item at every depth. Test in Step 1: `finds_test_items_at_any_depth`.
5. **Tests generated by a macro outside any `#[cfg(test)]` item** (a top-level `proptest! { ... }` in a `src` file) are counted as library code. None exist today (`grep -rn "proptest!" libs/*/src examples/*/src` is empty). Accepted and documented in CONTRIBUTING's Coverage section as part of the inline-tests rule; no test.

## 4. Deviations

Found by the probe and the local run on 2026-11-12 (cargo-llvm-cov 0.9.1, LLVM 23.1.1 from Rust 1.99.1, macOS):

1. **`cargo-llvm-cov` skips every `examples/` directory by default** (its default ignore regex covers `tests`, `examples` and `benches`), which dropped `fixed_step_sim` from the lcov. Both report commands now pass `--no-default-ignore-filename-regex`. With the default off, dependency sources (`~/.cargo/registry/src/...`) and the standard library (`/rustc/<hash>/...`) are no longer filtered, so `ignore_regex` gained two alternatives, `|/(registry/src|git/checkouts)/|^/rustc/`; the summary's path check remains the safety net for anything else. Spec §4.3's sentence "Dependency sources are already excluded by `cargo-llvm-cov`" is corrected. R3 holds: only `libs/*/src` and `examples/*/src` are counted. The test `ignore_regex_lists_the_excluded_dirs` pins the longer string.
2. **No `engine` row.** The facade crate has no instrumented line (it only re-exports), so it has no `SF` record and the table has five rows plus `Total`, not six. The verification's "exactly the rows" list in Step 3 is therefore without `engine`.
3. **The HTML and the lcov count lines differently, so R16's cross-check does not hold exactly.** HTML total lines 2954; lcov `DA` lines 2900, which is the table's 1853 counted plus 1047 excluded, exactly. The per-file HTML counts are 1 to 4 percent higher (for example `lib.rs` of `fixed_step_sim`: 121 in the HTML, 119 `DA`). The table is consistent with its own input; the HTML is not the same measure. CONTRIBUTING says the HTML percentages are higher, and does not promise an exact difference.
4. **`FN` has no end line and names are mangled** (`FN:146,_RNvM...`), so the optional end-line form is handled by the parser and its test but does not occur with this toolchain. Names contain no commas, so the comma test is a guard for demangled output only.
5. **A benign warning** from `cargo llvm-cov report`: `88 functions have mismatched data` (profiles from several test binaries; generic instantiations). It does not fail the run and the numbers are unaffected.
6. **Step 1 and 2 tests were written together with the code in one pass for Step 1** (the finder and its six tests), so the red run for Step 1 was replaced by a mutation check (making `requires_test` always false failed four of the six tests). Steps 2 and 3 were run red first (compile errors) as planned.
7. **Local checks used the scratchpad for the symlink** instead of `/tmp`; the table was identical to the direct run.
