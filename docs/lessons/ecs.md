# Lessons: ECS prototypes and queries

- Status: Living (2026-11-20)

Add `libs/engine/src/ecs/**` to `applies_to` when M4 creates that module.

- **ecs-1.** A test that checks which path a query takes builds the query through the same function the measured `step` uses, never a copy of its type, and reports the path by calling the same named gate the loop calls (a `const fn`), never a parallel description such as the query's type list or a copy of the gate's expression. *Why:* M3.3's path tests wrote out their own read-only copies of each step query, so changing a step's `&mut Lifetime` to `Option<&mut Lifetime>` sent the grouped backend down the view path while conformance and the path test both still passed (code review); in M3.5 `probed()` was built from the entry list, so a wrong `PROBES` constant would have put a probe in every table-only loop while every path test passed (conditional review). *From:* M3.3, M3.5 · *Confirmed:* 2026-11-20
- **ecs-2.** A spec or plan that defers per-query state ("it is only X per query") counts the allocations and lookups of the code as built before close-out, and records that cost as a caveat for whoever reads the numbers; it also checks whether a run's setup grows with the number of registered types rather than the types the query names. Count allocations from outside the crate: a scratchpad crate with its own `[workspace]` table and a `rust-toolchain.toml` pin, depending on the spike by path, with its own counting `#[global_allocator]` (or `dhat`); a counting allocator needs `unsafe`, which spike crates forbid. *Why:* M3.3's spec deferred cached query state for "a few `BTreeMap` lookups", but each query run made about five heap allocations inside every measured `step` (performance review); in M3.4 a builder lifted `forbid(unsafe_code)` in the working tree to count them; M3.19's spec said `frag_iter`'s 26 letter types cost nothing in the step, but every `QueryMut` run collects all 27 columns (performance review). *From:* M3.3, M3.4, M3.19 · *Confirmed:* 2026-11-20
- **ecs-3.** In a sealed query trait, the item GAT (`type Item<'w>`) goes on the private seal trait, not the public one; the public trait names it through its supertrait. *Why:* on rustc 1.100, seal methods that named `<Self as QueryParam>::Item<'a>` under `where Self: QueryParam` made the other associated types fail to normalize in impls (E0053, E0599), in M3.3 step 3. *Retire when:* the compiler normalizes that projection. *From:* M3.3 · *Confirmed:* 2026-11-19
- **ecs-4.** A `# Panics` or error doc that says the world (or a count) is unchanged after a failure is tested on the cold path, the first call of its kind, and the test asserts the panic's own message, not just that something panicked. *Why:* M3.4's `spawn_with` builds and caches its bundle's archetype before the allocator check, so a cold failure left a new archetype behind although the doc said "unchanged"; the only test warmed the cache first, and the cold test as first written passed on any panic (three reviewers). *From:* M3.4 · *Confirmed:* 2026-11-20
- **ecs-5.** A claim that a borrow handed out of a storage "cannot change a length" is checked against every method of what it hands out, including crate-internal helpers on the query path and each sibling accessor when one is narrowed: `&mut dyn Trait` exposes all of the trait's methods, `&mut Box<dyn Trait>` also lets the caller replace the box, and `&mut Column<T>` exposes the column's own `insert` and `remove`. Hand out a newtype that offers only slices or `get` instead, and narrow it in the module that owns the storage: a `pub(crate)` accessor that returns `&mut [Box<dyn Trait>]` or `&mut [Archetype]` to the query module has already given the access away, even if the query code narrows it next. *Why:* M3.4's `Table::columns_mut` returned `&mut [Box<dyn ErasedColumn>]`, whose `swap_remove_*` methods let any crate code break T1 while the doc and spec said they could not (code review); in M3.19 a query helper `MutCx::take` handed out `&mut Box<dyn ErasedColumn>`, and once it was made private its sibling `take_mut` still returned the whole `&mut DenseColumn<T>` (two public API reviews); in M3.5 `World::parts_mut` returned the sparse-set boxes and archetypes to `query.rs` while the log said nothing left the storage modules (code and conditional reviews). *From:* M3.4, M3.19, M3.5 · *Confirmed:* 2026-11-20
- **ecs-6.** A red check for a storage bug (a despawn that leaves values behind, a remove that skips a column) is pointed at the storage's own tests or the model test, not at a workload's per-tick check, and its failures are listed with `cargo nextest run -p <package> --no-fail-fast` (then delete any `proptest-regressions/` it writes), since `cargo xtask test` stops at the first failure. *Why:* in M3.19 `entity_churn` respawns into every freed index in the same tick, so skipping the column clear in `despawn` was overwritten before `entity_churn_keeps_invariants_every_tick` ran, and the plan's red check did not fail; `despawn_clears_every_column` and the model test did. In M3.5 a fail-fast run named two tests for a red check and hid the two the plan named, which did fail. *From:* M3.19, M3.5 · *Confirmed:* 2026-11-20
- **ecs-7.** When a prototype's hot-path operation (`insert`, `remove`, spawn) is adapted from a sibling backend, its map lookups and downcasts per call are compared with the sibling's before benchmarks are run. *Why:* M3.19's `World::insert` looked the type up twice where M3.3's looks it up once, on the very workloads the spec named as the model's best case, so M3.8 would have read the extra lookup as a cost of the storage model (code and performance reviews). *From:* M3.19 · *Confirmed:* 2026-11-20
- **ecs-8.** In a seal trait whose fetch GAT carries a lifetime (`type Ref<'w, T>`), a method whose lifetime appears only inside that projection (`fn row<'w>(f: &Self::Ref<'w, T>) -> &'w T`) has an early-bound lifetime, so each impl writes `Self::Ref<'w, T>` rather than the concrete type, and a reborrowing fetch spells out `'w: 'a` (`get<'a, 'w: 'a>(f: &'a mut Self::Fetch<'w>)`), since no implied bound comes through a projection. *Why:* on rustc 1.100 M3.5's builder met E0195 ("lifetimes do not match") on every impl that named `&'w [T]`, and missing-bound errors on the reborrowing `get`, before the query module compiled. *Retire when:* the compiler treats those lifetimes as late-bound. *From:* M3.5 · *Confirmed:* 2026-11-20
- **ecs-9.** A per-archetype fetch for a required column is bound so its length is exactly the table's row count on every path (`&col[..len]`, with a panic if the column is missing), never through a fallback such as `map_or(&[], …)` whose length is "len or 0"; then the first informal run's iteration numbers are compared with the sibling backend's before anything is quoted. *Why:* M3.5's hybrid `simple_iter` ran at twice `archetype`'s time with the same step body: the "len or 0" fetch gave the vectorized loop alias checks that always failed (two compared an array with itself), so it ran the scalar path; no test can see it, only the benchmark and the assembly did. *From:* M3.5 · *Confirmed:* 2026-11-20
