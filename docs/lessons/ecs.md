# Lessons: ECS prototypes and queries

- Status: Living (2026-11-26)

Add `libs/engine/src/ecs/**` to `applies_to` when M4 creates that module.

- **ecs-1.** A test that checks which path a query takes builds the query through the same function the measured `step` uses, never a copy of its type, and reports the path by calling the same named gate the loop calls (a `const fn`), never a parallel description such as the query's type list or a copy of the gate's expression. A grouped path test checks that the group matches the query exactly (no type probed per row), not only that a group is taken. *Why:* M3.3's path tests wrote out their own read-only copies of each step query, so changing a step's `&mut Lifetime` to `Option<&mut Lifetime>` sent the grouped backend down the view path while conformance and the path test both still passed (code review); in M3.5 `probed()` was built from the entry list, so a wrong `PROBES` constant would have put a probe in every table-only loop while every path test passed (conditional review); in M3.26 `uses_group()` held for a three-type group under the four-type `heavy_compute` query, which then probes `Velocity` per row, so narrowing the group passed every test (conditional and code review). *From:* M3.3, M3.5, M3.26 · *Confirmed:* 2026-11-26
- **ecs-2.** A spec or plan that defers per-query state ("it is only X per query") counts the allocations and lookups of the code as built before close-out, and records that cost as a caveat for whoever reads the numbers; it also checks whether a run's setup grows with the number of registered types rather than the types the query names. Count allocations from outside the crate: a scratchpad crate with its own `[workspace]` table and a `rust-toolchain.toml` pin, depending on the spike by path, with its own counting `#[global_allocator]` (or `dhat`); a counting allocator needs `unsafe`, which spike crates forbid. *Why:* M3.3's spec deferred cached query state for "a few `BTreeMap` lookups", but each query run made about five heap allocations inside every measured `step` (performance review); in M3.4 a builder lifted `forbid(unsafe_code)` in the working tree to count them; M3.19's spec said `frag_iter`'s 26 letter types cost nothing in the step, but every `QueryMut` run collects all 27 columns (performance review). *From:* M3.3, M3.4, M3.19 · *Confirmed:* 2026-11-20
- **ecs-3.** In a sealed query trait, the item GAT (`type Item<'w>`) goes on the private seal trait, not the public one; the public trait names it through its supertrait. *Why:* on rustc 1.100, seal methods that named `<Self as QueryParam>::Item<'a>` under `where Self: QueryParam` made the other associated types fail to normalize in impls (E0053, E0599), in M3.3 step 3. *Retire when:* the compiler normalizes that projection. *From:* M3.3 · *Confirmed:* 2026-11-19
- **ecs-4.** A `# Panics` or error doc that says the world (or a count) is unchanged after a failure is tested on the cold path, the first call of its kind, and the test asserts the panic's own message, not just that something panicked. *Why:* M3.4's `spawn_with` builds and caches its bundle's archetype before the allocator check, so a cold failure left a new archetype behind although the doc said "unchanged"; the only test warmed the cache first, and the cold test as first written passed on any panic (three reviewers). *From:* M3.4 · *Confirmed:* 2026-11-20
- **ecs-5.** A claim that a borrow handed out of a storage "cannot change a length" is checked against every method of what it hands out, including crate-internal helpers on the query path and each sibling accessor when one is narrowed: `&mut dyn Trait` exposes all of the trait's methods, `&mut Box<dyn Trait>` also lets the caller replace the box, and `&mut Column<T>` exposes the column's own `insert` and `remove`. Hand out a newtype that offers only slices or `get` instead, and narrow it in the module that owns the storage: a `pub(crate)` accessor that returns `&mut [Box<dyn Trait>]` or `&mut [Archetype]` to the query module has already given the access away, even if the query code narrows it next. *Why:* M3.4's `Table::columns_mut` returned `&mut [Box<dyn ErasedColumn>]`, whose `swap_remove_*` methods let any crate code break T1 while the doc and spec said they could not (code review); in M3.19 a query helper `MutCx::take` handed out `&mut Box<dyn ErasedColumn>`, and once it was made private its sibling `take_mut` still returned the whole `&mut DenseColumn<T>` (two public API reviews); in M3.5 `World::parts_mut` returned the sparse-set boxes and archetypes to `query.rs` while the log said nothing left the storage modules (code and conditional reviews). *From:* M3.4, M3.19, M3.5 · *Confirmed:* 2026-11-20
- **ecs-6.** A red check for a storage bug, or a test that pins a narrowed invariant check, puts its corrupting write in the region only the new or changed check covers; a red check for a storage bug (a despawn that leaves values behind, a remove that skips a column) is pointed at the storage's own tests or the model test, not at a workload's per-tick check, and its failures are listed with `cargo nextest run -p <package> --no-fail-fast` (then delete any `proptest-regressions/` it writes), since `cargo xtask test` stops at the first failure. *Why:* in M3.6 the test for a check narrowed to "bytes past the values" dirtied a byte in the block still in use, which the old check already caught, so a regression would have passed (code review); in M3.19 `entity_churn` respawns into every freed index in the same tick, so skipping the column clear in `despawn` was overwritten before `entity_churn_keeps_invariants_every_tick` ran, and the plan's red check did not fail; `despawn_clears_every_column` and the model test did. In M3.5 a fail-fast run named two tests for a red check and hid the two the plan named, which did fail. *From:* M3.19, M3.5, M3.6 · *Confirmed:* 2026-11-23
- **ecs-7.** When a prototype's hot-path operation (`insert`, `remove`, spawn) is adapted from a sibling backend, its map lookups and downcasts per call, and a new query path's dynamic calls and downcasts per matched table, are compared with the sibling's before benchmarks are run. A baseline backend on an external library is checked the same way: its iteration form (`for_each`, which takes the library's specialized `fold`, not a `for` loop over `next()`), its reused buffers' capacity in `setup`, and the per-call cost of the library API it uses for deferred changes, read in the library's source. *Why:* M3.19's `World::insert` looked the type up twice where M3.3's looks it up once, on the very workloads the spec named as the model's best case, so M3.8 would have read the extra lookup as a cost of the storage model (code and performance reviews). In M3.6 the raw query called `describe` on every column and downcast every byte column of a matched table, fetched or not, where the typed query downcasts fetched columns only (code and performance reviews). M3.10's bevy and hecs steps were `for` loops where every prototype uses `for_each` (main session's read), and its hecs `agents` applied inserts through `CommandBuffer`, whose keyless dynamic bundles skip hecs's cached insert edges (performance review). *From:* M3.19, M3.6, M3.10 · *Confirmed:* 2026-11-23
- **ecs-8.** In a seal trait whose fetch GAT carries a lifetime (`type Ref<'w, T>`), a method whose lifetime appears only inside that projection (`fn row<'w>(f: &Self::Ref<'w, T>) -> &'w T`) has an early-bound lifetime, so each impl writes `Self::Ref<'w, T>` rather than the concrete type, and a reborrowing fetch spells out `'w: 'a` (`get<'a, 'w: 'a>(f: &'a mut Self::Fetch<'w>)`), since no implied bound comes through a projection. *Why:* on rustc 1.100 M3.5's builder met E0195 ("lifetimes do not match") on every impl that named `&'w [T]`, and missing-bound errors on the reborrowing `get`, before the query module compiled. *Retire when:* the compiler treats those lifetimes as late-bound. *From:* M3.5 · *Confirmed:* 2026-11-20
- **ecs-9.** A per-archetype fetch for a required column is bound so its length is exactly the table's row count on every path (`&col[..len]`, with a panic if the column is missing), never through a fallback such as `map_or(&[], …)` whose length is "len or 0"; then the first informal run's iteration numbers are compared with the sibling backend's before anything is quoted. *Why:* M3.5's hybrid `simple_iter` ran at twice `archetype`'s time with the same step body: the "len or 0" fetch gave the vectorized loop alias checks that always failed (two compared an array with itself), so it ran the scalar path; no test can see it, only the benchmark and the assembly did. *From:* M3.5 · *Confirmed:* 2026-11-20
- **ecs-10.** Code that moves or decodes values whose size is a runtime value (byte columns, codecs) fixes the length by type where it can (an array `[u8; N]`, a slice cut to `4 * N` once, a `match` over common sizes), and the first informal run of a per-row loop is checked in the assembly for `memcpy`, `memmove` or `bzero` calls before its numbers are read as the design's cost. *Why:* in M3.6 a codec helper over a slice of unknown length made five libc calls per entity and the byte column's moves nine, so the copy path ran 34 times `archetype` and `add_remove` twice it; fixed lengths brought them to 1.9 and 1.4 times (diagnosis, log.md). *From:* M3.6 · *Confirmed:* 2026-11-23
- **ecs-11.** Where a conformance checksum cannot see a piece of state, a test asserts that state directly after each step and is checked by removing the write it guards: a type stored under one of two wrappers or storages (`Table<B>` or `Sparse<B>`), where the test asserts the other was never registered; a field the hash leaves out on purpose (a backend's entity handle), where the test asserts the invariant the write keeps. *Why:* in M3.10, flipping `Sparse(B)` to `Table(B)` in `bevy_ecs_sparse`'s `add_remove` insert passed all 17 bevy tests, because each checksum reads the value only through the wrapper it expects (code review). In M3.21 `Target`'s handle is not hashed, so deleting pass B's retarget write-back passed every test on six backends while stale handles piled up and each row did two lookups per orphan (code and conditional reviews); the per-step test added then fails exactly when the write is removed. *From:* M3.10, M3.21 · *Confirmed:* 2026-11-24
- **ecs-12.** A test that needs a despawned entity whose index is still free, as distinct from a stale handle whose index was reused, orders its spawns and despawns against the allocator's free list, which reuses indices last in, first out (`libs/engine/src/genid/slots.rs`): despawn the entity after any reuse setup and assert before anything else spawns, with an `assert_ne!` on the two indices so the cases cannot merge again. *Why:* M3.21's four `Lookup` agreement tests despawned `dead` and then spawned `old`, which took `dead`'s index, so the "despawned" case was a second reused-index case and a `get` wrong only on a vacant slot would have passed (code review). *From:* M3.21 · *Confirmed:* 2026-11-24
- **ecs-13.** A new workload's update rule is simulated over the conformance run before its spec is approved, to show the state still changes at the last compared tick, and the reference backend gets a test that every tick's checksum differs from every earlier tick's (tick 0 included); each figure the spec quotes from the simulation is written to `log.md`. *Why:* M3.22's first `update` (`w * 0.5 + r * 0.25 + 0.125`) was a contraction that froze every value at 0.5 by about tick 18, so ticks 18 to 120 of every conformance test compared checksums that could not differ; the spec reader's simulation caught it, and a rule that wraps in `0.0..1.0` replaced it. M3.26 found the same in two existing rules: `frag_iter` froze at tick 26, and `heavy_compute`'s checksum changed at every tick (so "differs from the one before" passed) while 77 of 120 equalled an earlier tick's; two of the spec's simulated figures were missing from the log until review. *From:* M3.22, M3.26 · *Confirmed:* 2026-11-26
