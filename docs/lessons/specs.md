# Lessons: writing specs and plans

- Status: Living (2026-11-27)

- **specs-1.** A §8 check written as "finds nothing" names the paths it covers. *Why:* `git grep 'design/m[0-9]'` also matched historical records that quote the old paths on purpose, so the check could never pass as written (M3.15). *From:* M3.15 · *Confirmed:* 2026-11-15
- **specs-2.** Evidence that §8 says will be "noted in `log.md`" is its own plan step, or it is forgotten. *Why:* M3.15's R7 follow-up note was missing until the spec review asked for it. *From:* M3.15 · *Confirmed:* 2026-11-15
- **specs-3.** When a spec asks for a test per row of a table (every panic of §4.x, every operation), or its §8 names the operations a test runs (a model test over `spawn`, `despawn`, `insert`, `remove` and `apply`), the plan names one test per row and copies those operations into the step's test list. *Why:* M3.17's plan named the panic tests loosely, and four of §4.5's rows (`ensure_capacity`, both `Extend`s, `From<[usize; N]>`) shipped untested until review; M3.3's plan listed the model test's operations without `apply`, so R5's evidence was missing until the spec review. *From:* M3.17, M3.3 · *Confirmed:* 2026-11-19
- **specs-4.** Evidence recorded in `log.md` names the commit it ran on; a library or measured-code change after it (a review fix, a simplify pass) means re-running it or saying in the pull request that it predates the change. *Why:* M3.17's fuzz, wasm, full `ci` and `bench-regress` entries predated three later library commits, and the spec review could not tell which code they covered. In M3.6 the simplify pass and two review rounds changed measured spike code after the allocation counts and the informal run, so both were re-run on the final code (four reviewers flagged it). *From:* M3.17, M3.6 · *Confirmed:* 2026-11-23
- **specs-5.** When a spec rejects wrapping a crate but builds our own version of its design, the plan has a step that cites the design in the shipped rustdoc (ADR 0002), not only in the spec. *Why:* M3.17 followed `hibitset`'s design and cited it only in the spec until the security review. *From:* M3.17 · *Confirmed:* 2026-11-16
- **specs-6.** A log line or caveat that names the cause of a measured gap says how the cause is known (measured by a variant, read from the assembly, or expected and unmeasured), and one that blames the spec's design cites the spec text that requires the work. *Why:* M3.6's log first stated two causes as fact that only one variant had measured, and gave "the zero tail spec §4.3 requires" a cost that came partly from a stricter block-count check the spec did not ask for, which M3.8 would have read as a cost of byte columns (docs and performance reviews). *From:* M3.6 · *Confirmed:* 2026-11-23
- **specs-7.** A spec sentence that describes how existing code works (a backend's join, a planner's choice) is checked against that code in the grill; when a later step finds it wrong, the spec is amended in the same chunk, not only noted in `log.md` or the plan. *Why:* M3.25's spec said `dense` joins its presence bitsets over the whole index space, but the join is over `HierarchicalBitSet`s that skip empty regions; noted only in the log and plan, the Accepted spec contradicted the README until two docs reviews asked for the amendment. *From:* M3.25 · *Confirmed:* 2026-11-27
